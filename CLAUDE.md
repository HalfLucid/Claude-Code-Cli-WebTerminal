# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Build: **before running `dotnet build`, check if webterm is running** (`Get-Process webterm -EA SilentlyContinue`). If running, skip the build — the DLL is locked and it will fail. The user will restart webterm themselves to pick up changes.
- Run (dev): `dotnet run` — launches on `http://localhost:5265` (and `https://localhost:7044` via `https` profile) per `Properties/launchSettings.json`.
- Binding: `ConfigureKestrel` in `Program.cs` listens on `https://0.0.0.0:7681` (`HttpsPort`, self-signed cert stored DPAPI-encrypted in settings) and plain `http://localhost:7680` (`LoopbackHttpPort`, for the notify hook and `claude mcp add`), overriding `launchSettings.json`.
- Publish: `dotnet publish -c Release`
- Windowless: the exe is `WinExe`, so it opens no console window of its own (Startup shortcut from `/api/startup`, `restart`, which spawns its build/run PowerShell hidden). `ConsoleHost.AttachToParent()` borrows the parent's console when there is one (`dotnet run`, a terminal), and the first-run prompt `AllocConsole`s its own unless the parent is `dotnet` (the only parent that waits for a GUI exe; a shell that started it directly is back at its prompt reading the same keys), also replacing the hidden restart console (flagged by `WEBTERM_HIDDEN_CONSOLE=1`, which is cleared so spawned shells don't inherit it); it re-asks on invalid input instead of exiting. Once credentials are saved, a console it opened is closed (`ConsoleHost.ReleaseOwned`: `Console.Out`/`Error` set to `TextWriter.Null` first, since the cached writers would throw on the freed handle), so closing that window or Ctrl+C can't kill the server. `Log` also appends to `webterm.log` beside the exe (rotated to `webterm.log.old` past 5 MB).
- Tray icon (`Tray.cs`, WinForms `NotifyIcon` on its own STA thread, icon drawn at runtime): left-click opens `https://localhost:7681`; menu has live-session count, Open log, Restart (rebuild), Exit (both confirm when sessions are live, since they kill every PTY). Exit disposes the sessions and calls `Environment.Exit` rather than `StopApplication`, which would wait ~30 s for open SSE/WebSocket requests. Restarts from the tray, `/api/restart` and MCP all go through `SpawnRestart`, whose hidden PowerShell opens the build output in Notepad if `dotnet build` fails (otherwise a failed restart would leave nothing running and nothing visible). If no `.csproj` is found above the exe (a published copy elsewhere), it skips the build and just relaunches the same exe with the same arguments and working directory once the old process has exited.
- The TFM is `net10.0-windows` (for WinForms), with `OutputPath` pinned to `bin\<Config>\net10.0\` so the existing `webterm-settings.json` and Startup shortcut keep working. WinForms/Drawing implicit usings are removed to avoid type clashes in `Program.cs`.

No test project exists.

## Architecture

ASP.NET Core minimal API (`Program.cs`) + static frontend (`wwwroot/`) that exposes a browser-based terminal via WebSocket-to-PTY bridge with persistent, multi-tab sessions.

### Server (Program.cs)

**Endpoints:**
- `GET /` — serves `wwwroot/index.html` via `UseDefaultFiles` + `UseStaticFiles`
- `Map /ws?sid=<guid>[&from=<offset>&cols=<c>&rows=<r>]` — WebSocket upgrade; looks up or creates a `Session` keyed by `sid`; `from` resumes replay at a byte offset, `cols`/`rows` are the client's grid (see Resumable replay)
- `GET /api/settings` — returns projects, button config (no credentials)
- `POST /api/projects` — add Claude project (name, directory, color)
- `PUT /api/projects/{id}` — update project
- `DELETE /api/projects/{id}` — remove project
- `PUT /api/buttons` — update button order + custom buttons
- `GET /api/sessions` — returns all active sessions with metadata (sid, kind, label, color, projectId, launched, connected). Server is source of truth for tab list; replaces localStorage persistence.
- `GET /api/events` — SSE (Server-Sent Events) stream for real-time tab notifications. Events: `tab_opened`, `tab_closed`, `tab_attention`, `tab_idle`, `show_file`, `copy_text`. Browser subscribes via EventSource on page load.
- `POST /api/notify?token=<key>` — receives Claude Code hook notifications (`{sid, event}`). Maps `permission_request` → `tab_attention` SSE, `stop` → `tab_idle` SSE. Auth via MCP token, exempt from Basic auth.
- `POST /api/upload?sid=<sid>` — multipart upload of files pasted/dropped in the browser. Writes them to the tab's upload dir and returns `{paths: [...]}` (absolute host paths). 20 MB per file.
- `GET /api/transcript/{sid}?from=<offset>&path=<path>` — the tab's agent conversation, read from the agent's own `.jsonl` log (Claude's, or agy's; see History overlay) and distilled to display entries for the history overlay (see History overlay). Incremental: returns `{path, offset, reset, items}`; pass back `offset` and `path` to get only new entries. `path` null when no log is found (PowerShell tab, or the agent hasn't written yet).
- `GET /api/transcript/{sid}/image?path=<log>&at=<line offset>&n=<index>` — one base64 image from a Claude log, decoded (`Transcript.Image`), for the history overlay's thumbnails. `path` must pass `Transcript.IsValidPath` and be a log `Session.TranscriptPath` has handed out for that sid (`HasServedTranscript`; kept across `/clear`). Only `image/png|jpeg|gif|webp` are served (an SVG opened directly would run script in WebTerm's origin), with `X-Content-Type-Options: nosniff`.
- `GET /api/transcript/{sid}/file?path=<log>&at=<line offset>&n=<index>` — a file Claude showed with `show_file`, found again through the `n`th `mcp__webterm__show_file` call on that log line (`Transcript.ShownFile`; not a sidechain, and only once a `tool_result` for the call without `is_error` follows it within 16 MB, so a denied call's file is never served), so the history overlay can show it after the transient `/api/file` id is gone. Same log checks as the image endpoint; only what `Transcript.MediaKind` accepts (raster images, video, audio; no SVG), range-enabled, `nosniff`.
- `GET /api/file/{id}` — serves a file registered by the MCP `show_file` tool, by its transient id. Range-enabled so video/audio can seek. 404 once the id is gone (dismissed client-side, or evicted by the 50-entry cap).
- `DELETE /api/file/{id}` — drops the id→path reference (the source file on disk is never touched). Called when the viewer overlay is dismissed.
- `POST /api/mcp-setup` — generates DPAPI-encrypted MCP API key (if not exists), installs the agents' hooks for tab notifications, returns a PowerShell command that registers WebTerm with each agent CLI found on PATH (`claude mcp add …`, `agy mcp add …`) with the token. Idempotent.
- `POST /mcp?token=<key>` — MCP server endpoint (JSON-RPC 2.0, Streamable HTTP transport). Tools: `open_tab`, `close_tab`, `list_tabs`, `restart`, `show_file`, `copy_text`. Auth via token query param, exempt from Basic auth middleware.

**First-run setup:** If no `webterm-settings.json` exists beside the exe, prompts for username/password in console before starting the web server. Credentials are encrypted with Windows DPAPI (`ProtectedData`, `DataProtectionScope.CurrentUser`) and stored in the settings file.

**Browser auto-open:** On `ApplicationStarted`, opens default browser to `https://localhost:7681`.

**Middleware order:** auth (exempts `/mcp` and `/api/notify`) → WebSockets → DefaultFiles → StaticFiles → route mappings.

### Settings file (`webterm-settings.json`, beside exe)

JSON with: `credentials` (DPAPI-encrypted), `projects` (array of {id, name, directory, color, agent}; `agent` is the agent id its Open/Resume buttons launch, default `claude`), `buttons` (order array + custom buttons), `defaultPowershellColor`, `mcpKeyProtected` (DPAPI-encrypted MCP API key, generated on first "Add MCP" click).

### Session persistence (decoupled PTY lifetime)

`Session` (sealed class in `Program.cs`) owns one `IPtyConnection` per client `sid`. Sessions live in a process-global `ConcurrentDictionary<string, Session>`. PTY lifetime is **independent of the WebSocket** — disconnecting (screen sleep, network loss) does **not** kill the shell. Reconnecting with the same `sid` reattaches.

Key pieces inside `Session`:

- **Ring buffer**: `LinkedList<(long start, byte[] data)>` capped at `MaxBuffer = 2 MB` (≈ the client's 5000-line xterm scrollback of escape-heavy Claude output). `ReadLoop` reads from `Pty.ReaderStream`, appends to buffer, evicts oldest chunks, forwards via `TryWrite` to currently-attached channel.
- **Per-attachment send pump**: each `Attach` creates an `Attachment` (socket + `Channel<(bool text, byte[] payload)>` + abort deadline); its pump is the socket's only sender. Replay frames, PTY output, pongs and the final close all go through it, so no `SendAsync`/close ever overlaps. Ending an attachment (`EndAttachment`) completes the channel; the pump drains it, sends the close frame (`CloseOutputAsync`) if there is a reason, and the deadline `Abort()`s the socket 5 s later if the handshake hasn't finished. A single send stalled for 60 s also aborts. Abort callbacks run on timer threads, so they swallow exceptions (an unhandled one kills the process), and `Attachment.Disarm()` unregisters the deadline's callback before `Attach` returns, since aborting after ASP.NET disposes the `HttpContext` throws. On PTY exit, `ReadLoop` ends the attachment with `"pty-exited"` and `{"ptyExited":true}` as its `FinalFrame`: the pump drops whatever output is still queued (the client removes the tab anyway), sends the final frame after the send in flight (if any), then the close. Queued behind a big replay on a slow link, the notice could outlast the 5 s deadline; the abort would make the client reconnect, and once the reaper had removed the session that reconnect would get `{choose}` and launch a fresh shell in the tab.
- **Replacement protocol**: a second client with the same sid takes over at once: its replay is queued under the session lock and the old attachment is ended with `"replaced"` without being awaited (a phone waking from sleep leaves a dead socket that would stall the new attach for the full close timeout). The live old client still receives the `"replaced"` close, which triggers its takeover popup. Its pump drops whatever output is still queued and sends that close right after the send in flight (if any) finishes; draining first could outlast the 5 s close deadline on a slow link, and the resulting abort (code 1006, no reason) would make the old client reconnect and replace the new one. (`"pty-exited"` skips the queue the same way, via `Attachment.SkipsQueue`; its `{ptyExited}` notice is the `FinalFrame`, sent before the close, so it is not dropped with the queue.) Until it closes, a replaced socket's input and resizes are ignored, and its teardown only clears the session's attachment if it is still current.
- **Resumable replay**: the client tracks `tab.recvOffset` (absolute PTY byte offset it has rendered) and reconnects with `/ws?sid=<sid>&from=<offset>&cols=<c>&rows=<r>`. On attach the server first sends a `{"offset":N}` text frame, then replays from `N`: the client's offset if it is still inside the ring buffer **and** the PTY size stayed at the client's `cols`×`rows` from there on (`SizeUnchangedSince`; otherwise xterm would reflow the screen it already has), else a point within the last `MaxReplay = 512 KB` (or the oldest buffered byte if the buffer holds less). Chunks are arbitrary 4 KB PTY reads, not ConPTY write boundaries, so `SafeReplayStart` scans up to 16 KB forward from the cap for a byte just before an ESC or just after a LF (else the first non-UTF-8-continuation byte), so the replay never begins inside an escape or UTF-8 sequence; `N` may be mid-chunk and is exactly the first byte sent. The cap keeps a fallback replay from stalling a phone for seconds (2 MB of escape-heavy output plus a reflow per size marker) with live output and typed echo queued behind it; the 2 MB ring buffer still lets short disconnects resume. A resume is never capped. If `N` differs from `tab.recvOffset` the client `term.reset()`s before the replay so output is never stacked twice. The reset goes through `queueReset` (inside a `term.write('', cb)`, like `queueResize`), because bytes from the previous socket may still be in xterm's write queue and an immediate reset would let them parse on top of the new replay. `hardRefresh` clears `recvOffset` to force a full replay, and queues its reset and `fit()` the same way.
- **Size-faithful replay**: output is laid out for the PTY size it was produced at, so `Session._sizes` records `(offset, cols, rows)` on launch and on every resize (pruned alongside the ring buffer). The offset frame carries the size in effect at `N` (`{"offset":N,"cols":c,"rows":r}`; 0 when unlaunched), `{"size":{cols,rows}}` text frames are interleaved with the replay bytes at the offsets where the size changed after `N` (earlier markers are folded into the offset frame's size, never sent), and `{"replayEnd":true}` closes it. The client applies each size via `queueResize` (a `term.write('', cb)` so the resize lands between the right bytes, since `term.resize` is synchronous but writes are queued). On `replayEnd` it sends its own size to the server immediately (via `proposeDimensions`, so it precedes any launch message), then fits xterm back to its container once the replay has drained. `tab.replaying` blocks `sendSize`/`forceResize` meanwhile. If the tab is hidden at `replayEnd`, nothing is sent and `tab.sentCols`/`sentRows` are cleared, so the `forceResize` on tab switch sends the size (it otherwise only sends when the grid differs from `sentCols`/`sentRows`). A capped replay adds `"truncated":true` to the offset frame: rows ConPTY drew before `N` and never redrew (e.g. the top of the screen during a long spinner) are missing, as are modes set before `N` (SGR, cursor visibility). No mode prefix is sent: the client's `term.reset()` already starts from defaults, the jiggle makes ConPTY repaint with absolute positioning and full SGR, and xterm's input modes are irrelevant because the client builds its own key sequences. The client tracks the PTY's size through the replay (`tab.replayCols`/`replayRows`) and, once it knows its own size (at `replayEnd`, or on tab switch if hidden), sets `tab.pendingJiggle` only if that size equals the PTY's: a different size is a real resize that already makes ConPTY/Claude repaint, and a jiggle on top would just print the transcript again (`jiggleIfTruncated` in `connection.js`).
- **Heartbeat**: after a network switch, sleep or Wi-Fi blip the browser can keep a socket at `readyState === 1` that the server already dropped, and JS can't see protocol pings. So the client records `tab.lastRecv` on every frame (replay included) and, while open, sends `{"ping":n}` every 15s; the server's receive loop answers `{"pong":n}` through the send pump (the attachment channel carries `(text, payload)` frames, since only the pump may `SendAsync`). No frame for 35s → the socket is dropped and `scheduleReconnect` runs; `recvOffset` is kept, so it resumes rather than wipes. Hidden pages run timers late, so that check only fires on a visible, on-time tick; instead `reconnectIfNeeded` (visibilitychange/online) pings a socket that looks open but has been quiet >5s and reconnects if nothing arrives within 3s. A socket can also hang at `readyState === 0` after a network switch, before the heartbeat starts, so `connect` arms a 10s connect timeout (`tab.connectTimer`, cleared on open, close and `disconnect`) that drops it the same way and goes through `scheduleReconnect`.
- **Metadata**: each session stores `Kind`, `Label`, `Color`, `ProjectId` — set during `Launch()` or from browser's launch JSON. Enables `GET /api/sessions` and MCP `list_tabs`.
- **Reaper**: background task scans every minute and `Dispose()`s a session when `Session.ReapReason` returns a reason: its PTY has exited (reaped at the next scan); it has no PTY (never launched, or the spawn failed) and no socket has been attached for 10 minutes (`UnlaunchedReapAfter`); or its PTY is live but no socket has been attached **and** `ReadLoop` has seen no output for 24 hours (`SilentReapAfter`). Detaching alone never kills a live PTY, so a phone asleep for hours doesn't end a Claude session that is working or waiting at its prompt. The reason is logged on the `SESSION REAPED` line, and a `tab_closed` SSE event is broadcast.
- **Agents** (`Agents.cs`): the agent CLIs a tab can run, each an `AgentDef` (id, display name, exe, resume args, prompt args, process names): `claude` (Claude Code; `--resume`) and `agy` (Antigravity CLI; `--continue`, prompt via `-i`). A tab's kind is `powershell`, an agent id, or `<id>-resume`; `Agents.Parse` maps it, and an unknown kind is rejected (the WS launch logs it and launches nothing; MCP `open_tab` returns an error). The client mirrors the list in `AgentInfo` (`settings.js`) for display names.
- **Launch**: `Launch(kind, projectId, settingsManager, sid)` — looks up project directory from settings. PowerShell sessions spawn via `powershell.exe`. Agent sessions spawn via `cmd.exe /K <exe>` (plus the agent's resume args for `-resume`), with `WEBTERM_SID` and `WEBTERM_NOTIFY_TOKEN` environment variables injected for hook notifications.

### Client (wwwroot/)

**File structure:**
- `index.html` — HTML shell with tab bar, terminal container, main screen, button overlay, modals
- `css/style.css` — all styles
- `js/settings.js` — API calls to `/api/settings`, `/api/projects`, `/api/buttons`
- `js/terminal.js` — xterm.js instance factory (create/destroy per tab); loads the Unicode 11 addon so glyph widths match ConPTY, and the WebGL renderer (grid-locked glyphs; falls back to DOM on context loss)
- `js/connection.js` — per-tab WebSocket management, reconnect logic, resize
- `js/buttons.js` — configurable button overlay with model/effort popouts
- `js/history.js` — `HistoryView`: the history overlay (Claude log rendered as reflowing HTML, minimal markdown renderer)
- `js/tabs.js` — multi-tab state, tab bar rendering, `createExternalTab()` for server/MCP-initiated tabs
- `js/mainscreen.js` — project launcher UI, project CRUD modals, button config modal, MCP setup button
- `js/app.js` — orchestrator (input bridge, resize handlers, visibility/online recovery, server session restore, SSE listener)

**Multi-tab architecture:**
- Each tab has its own `sid`, xterm Terminal, FitAddon, WebSocket, and container div
- Tab state sourced from server via `GET /api/sessions` on page load (replaces localStorage persistence)
- Real-time updates via SSE (`/api/events`): `tab_opened` creates tab, `tab_closed` removes tab, `tab_attention` / `tab_idle` trigger attention indicators
- Cross-device: any browser connecting sees all active sessions. Second device connecting to same sid replaces first (existing replacement protocol).
- `createExternalTab(sid, kind, projectId, label, color)` — creates tab for server-side session, sets `restored: true` (so a `{choose}` reply, meaning the server lost it, removes the tab) and `confirmed: true`
- **Tab removal vs. session deletion**: `TabManager.removeTab(tab, deleteSession)` drops a tab from this browser; it sends `DELETE /api/sessions/{sid}` (killing the PTY) only when `deleteSession` is set. Only the user's explicit close (`closeTab`) and the certainly-dead cases delete: `{ptyExited}` (process gone) and `{choose}` on a `restored` or `confirmed` tab (the server lost a session it had launched, and our socket just created an empty unlaunched one in its place). `{choose}` launches only for a tab this browser created that has never been confirmed, including after its first socket drops before the launch is processed; a confirmed tab never launches a second process. Everything inferred from the session list — `reconcileSessions`, SSE `tab_closed`, and `scheduleReconnect` after 5 failed reconnects (a 401 there reloads the page) — removes the tab locally only, so a guess can never kill a live session.
- **Confirmation**: `/api/sessions` lists a session only after its launch is processed, so a just-created local tab (slow link, socket still connecting) is legitimately absent. A tab is `confirmed` once its sid appears in `/api/sessions`, or its socket gets PTY output or an `{offset}` frame with a nonzero size (launched session). `reconcileSessions` and the 5-failure path drop only confirmed tabs that are missing from the list; tabs from `createExternalTab` start confirmed. Every route to `confirmed` is server evidence of a launch, so a `{choose}` on a confirmed tab means the session was lost (see above).

**Resize discipline:** every real PTY resize makes ConPTY repaint and Claude reprint its transcript, which stacks duplicate paragraphs in xterm's scrollback. So the mobile keyboard must never change the row count: `applyViewportSize()` keeps `#terminals` at its CSS (layout-viewport) height and `translateY`s it up by the keyboard-covered amount — but only as far as needed to keep the lowest row holding text or the cursor visible (`contentBottom()`), so a fresh session's prompt near the top isn't pushed off-screen. `term.onWriteParsed` → `Connection.scheduleSlide()` re-slides as output grows toward the keyboard. `sendSize()` only sends `{cols, rows}` (and scrolls to bottom) when the grid actually changed; `forceResize()` (tab switch, wake) always re-measures, fits and repaints but likewise only sends a changed size. On connect the size is sent at `replayEnd`, not on socket open.

**Main screen:** Full-page launcher (replaces old chooser modal). Shows PowerShell button + project list from settings. Each project has "Open <Agent>" and "Resume <Agent>" buttons for the agent chosen in its settings (Agent select in the project modal). Add/edit/delete projects via modal.

### Input bridge (browser ↔ PTY)

- **Binary frames** browser → server: written straight to `Pty.WriterStream`.
- **Text frames** browser → server: parsed as JSON; `{launch, projectId, label, color}` triggers `Session.Launch` (label/color stored as metadata), `{cols, rows}` triggers `Pty.Resize`.
- The hidden `#ta` textarea is the input source. On each input it diffs the current value against the text already sent (`sentText`), sends one `\x7f` (DEL) per code point after the first difference, then sends the new tail (see `rewrite()` in `app.js`). Never retransmit the whole value per keystroke — that makes long input O(n) per key and forces Claude to redraw the whole prompt. This is how mobile IME / autocorrect edits are reflected — preserve this contract if changing input handling.
- Special keys (Enter, Tab, Shift+Tab, Backspace, Delete, arrows, Home/End, PageUp/PageDown, Insert, Esc, Ctrl+letter) are intercepted in `keydown` and translated to raw escape sequences. Arrow, Home, and End keys support Ctrl and Shift modifier variants.
- **Ctrl+C / Ctrl+V**: if text is selected in the terminal, Ctrl+C copies it (no SIGINT); Ctrl+V is a no-op in `keydown` and lets the native `paste` event on `#ta` fire instead, so `clipboardData` is read from the paste gesture itself (no clipboard-read permission chip). The right-click menu's Paste still calls `navigator.clipboard.readText()` since it has no paste gesture to hook. When nothing is selected, Ctrl+C sends raw ^C as usual. All pasted text is normalized to LF and wrapped in bracketed-paste (`\x1b[200~...\x1b[201~`) so a multi-line paste is treated as one block instead of submitting per line. A paste bypasses `#ta`, so afterwards `#ta`/`sentText` are cleared; otherwise a later DEL-based diff would erase Claude's `[Pasted text]`/`[Image]` placeholder.
- **Right-click context menu**: xterm renders on canvas so the browser's native context menu has no Copy/Paste — a custom `.term-menu` overlay (in `terminal.js`) provides Copy and Paste items on right-click.
- **Image paste / drag-drop**: the PTY is a keystroke stream, so image bytes can't be sent down it, and HTML5 drag-drop never exposes a real filesystem path. Pasting or dropping a file therefore POSTs the bytes to `/api/upload`, and the returned absolute host path is typed into the PTY (bracketed paste, quoted if it contains spaces) — the same thing a native terminal does when you drag a file onto it. Claude Code detects the image path and attaches it. The path goes to the tab the upload started on (sent to it directly if the user switched tabs meanwhile, clearing that tab's saved `savedInput`/`savedSent` mirror as `sendPaste` clears the live one); a tab in the HTML view takes it as a message-box attachment instead (see History overlay). `dragover`/`drop` are `preventDefault`ed on `document`; without that the browser navigates away to the dropped image.
- **Upload directory**: `<project>\.webterm\uploads\` when the tab has a project, so the path is inside Claude's cwd and needs no Read approval. A self-ignoring `.webterm\.gitignore` (containing `*`) keeps the folder out of git. Tabs with no project (PowerShell) fall back to `%TEMP%\webterm-uploads\`. A background task sweeps files older than 24h, hourly.
- **Tab input persistence**: switching tabs saves and restores textarea value and `sentText`, so in-progress input survives tab switches.

### Button overlay

Configurable button bar on right side. Two states:
- **Collapsed:** shows only the `minimizedOnly` buttons, top to bottom — scroll-up and scroll-down (each with a small `●↑`/`●↓` jump button to its left), reload (with the 📌 entry pin to its left, see History overlay), and HTML (toggles the history overlay; reads TEXT while it is open). The jump buttons (`jumpToResponse` in `buttons.js`) look for lines starting with Claude Code's `●`/`⏺` bullet that aren't tool calls (`Name(args)` header, a following `⎿` line, or `(ctrl+o to expand)`), and only stop at the first such reply after a user prompt or the last one before the next prompt, i.e. the end-of-turn summary (`isJumpTarget`: walking up, or down, a column-0 `> `/`❯ ` prompt line must come before any other reply; tool calls in between are fine, and walking down off the end of the buffer counts). The history overlay applies the same rule to its bubbles. `●↑` scrolls to the nearest one starting above the viewport top and `●↓` to the nearest one below it, or to the bottom if there is none. Both are stateless (relative to `viewportY`), so they work alongside manual scrolling. The button flashes red when there's no match. `webtermBullets()` in devtools lists every bullet line and how it was classified. The reload button (`Connection.hardRefresh`: resets input state, wipes xterm, opens a fresh WebSocket so the ring buffer replays, then nudges the PTY one column narrower and back so ConPTY/Claude repaint the screen. A same-size resize is a no-op in ConPTY, which is why maximize/restore used to be the only reliable fix)
- **Expanded:** shows all configured buttons (enter, arrows, ctrl combos, model/effort popouts, custom buttons)

Button order and custom buttons are persisted in settings and configurable via the button config modal on the main screen. Model/effort buttons show popout panels with options (sends `/model <name>\r` to PTY).

### File viewer (`show_file` MCP tool)

Lets a Claude session push a file from the host filesystem into the browser without going through the upload path (this is host → browser; upload is browser → host).

- `McpShowFile` resolves the path, registers it in an in-memory `id -> absolute path` map (`pendingFiles`, capped at 50 entries, oldest evicted first), and broadcasts a `show_file` SSE event (`{id, name, caption, kind}`) to all connected browsers.
- The browser opens an overlay: images and video/audio play inline (video/audio autoplay with controls); other kinds show a download link. `kind` and `Content-Type` are derived from the file extension (`FileMeta` in `Program.cs`).
- Image view supports wheel-zoom, double-click-to-zoom, and pointer-based pan/pinch-zoom (mouse + touch), clamped so panning can't push the image out of view.
- Dismissing the overlay (Esc, ×, or clicking outside) calls `DELETE /api/file/{id}` to drop the id→path mapping — the source file on disk is never touched or moved.

### History overlay (reflowable Claude history)

The terminal's scrollback is replayed PTY output, laid out for the width it was produced at (Claude and ConPTY hard-wrap), so text printed while the PTY was narrow (e.g. on a phone) stays narrow on a wide screen; ConPTY/Claude only redraw the visible screen on resize. Claude Code itself writes every conversation to `~\.claude\projects\<cwd with non-alphanumerics as '-'>\<session id>.jsonl` (the file `--resume` reads), with the text unwrapped. The HTML button shows that instead.

- **Finding the log** (`Session.TranscriptPath`): the path every webterm-notify hook reports (the script reads Claude's hook JSON from stdin and forwards `transcript_path`; a `SessionStart` hook reports it at startup, resume, `/clear` and compact). Without it (setup not re-run, or Claude hasn't fired a hook yet) `Transcript.Guess` picks the newest log in the cwd's project folder written since launch and not claimed (reported or guessed) by another tab, sticking to it unless a newer file is created once it has stopped being written (`/clear`; within 10 s), so another Claude starting in the same folder doesn't take over a log that is still growing. The guess can pick a Claude running outside WebTerm in the same folder. Only `.jsonl` files under `~\.claude\projects` are served. A Claude started from inside a tab (e.g. `claude -p` from its Bash tool) inherits `WEBTERM_SID`, so the hook also sends its process ancestry (`chain`: `[{pid, name}]`, nearest first, one `Win32_Process` query); `/api/notify` ignores the event entirely (no transcript update, no SSE) when more than one `claude.exe`/`node.exe` sits between the hook and the PTY's process (`IsNestedClaude`). No chain (older hook script) or the PTY not in it counts as not nested.
- **agy logs** (`Transcript.Agy.cs`): agy writes `~\.gemini\antigravity-cli\brain\<conversation id>\.system_generated\logs\transcript.jsonl` (and `transcript_full.jsonl`, same steps with tool output untruncated, which is what its hooks report), one step per line: `USER_INPUT` (text inside `<USER_REQUEST>`) → `user`, `PLANNER_RESPONSE` → `assistant` (`content`) plus one `tool` per `tool_calls` entry (args are JSON-encoded strings, decoded and shown as `Key: value` lines), `GENERIC` → `result` (`status: ERROR` → `err`, the `error` text), `SYSTEM_MESSAGE` → `note`; `thinking` is dropped. A planner step k's n calls are answered by steps k+1…k+n in order, so call i and its result both get id `k+1+i` with no state between reads. `Transcript.Read` picks the processor by path (`IsAgyPath`), and `IsValidPath` accepts both agy file names. Without a hook report, `AgyGuess` picks the newest unclaimed agy log written since launch (agy keeps all conversations in one folder, so the cwd can't narrow it), with the same stickiness as `Transcript.Guess`. Images and `show_file` thumbnails aren't extracted from agy logs.
- **Parsing** (`Transcript.cs`): one entry per line; unknown types are skipped since the format is internal to Claude Code. Keeps user text, assistant text, tool calls (name, primary argument, input) and results, slash/`!` commands and their output, compact summaries and boundaries. A message typed while Claude was busy is queued and logged not as a user entry but as a `type: "attachment"` line with `attachment.type: "queued_command"` (its `prompt`), whether Claude takes it mid-turn or after; only `origin.kind: "human"` ones are shown (agent hand-backs and task notifications are queued the same way, with `peer`/`task-notification` origins). Images (in the user's message, or in a tool result, e.g. Claude reading a screenshot) become `image` items carrying `img: "<line offset>:<index>"` (and, in a tool result, the call's `id`, emitted before the result since the result closes the call); `ImagesIn` (one block's images) fixes the index order for both `Process` and `ImageBlocks`, so `/api/transcript/{sid}/image` can find the block again without the base64 ever going out with the transcript. A `show_file` call on an image, video or audio file is followed by a `file` item (`img: "<line offset>:<index>"` among that line's show_file calls, `name`, `media`), rendered as a visible `.h-media` row after the collapsed call: a thumbnail that opens in the file viewer, or a video/audio player (`preload='none'`), served by `/api/transcript/{sid}/file`. The row stays hidden and unloaded (`tab.hist.files`, by call id) until the call's result arrives, and is removed if that result is an error (denied or failed). A load error shows a tap-to-retry note. An `ExitPlanMode` call becomes a `plan` item (the `plan` markdown, `planFilePath`'s file name) instead of a tool row, rendered as a blue-bordered Claude bubble (`.h-plan`); its result attaches to it as a status line: `✓ Approved` (the approval result repeats the whole plan, so its text isn't shown) or `✗` plus what the user said. The call is logged before the user answers, so the plan sits right above the mirrored approval menu. Drops meta entries, sidechains, thinking and `<system-reminder>` blocks. Long text is clipped; at most 5000 entries per read. The file is streamed in 64 KB chunks (only a line split across chunks is copied), so a long log isn't held in memory. Only complete lines are consumed, so the returned offset never splits a line Claude is still writing.
- **Client** (`history.js`): a full-height overlay above the terminal (z-index 15, under the button bar) that polls every 2 s while open and visible, appending new entries; rendered entries are cached per tab (`tab.hist`). Tool results attach to their call by id, collapsed in `<details>`; an open call's summary (drawn ▸/▾ arrow) is `position: sticky` at the top, so it can be collapsed from anywhere in a long output, and collapsing scrolls it back into view if it was above the top. **HTML is the default view**: each tab remembers its view in `tab.view` (`'html'`/`'text'`, unset = HTML for Claude tabs, terminal for PowerShell), and `switchTo` (and "back to session") reopens the overlay via `HistoryView.restore` when that view is HTML. Esc (captured before `#ta`, so it never reaches Claude), ×, the HTML/TEXT button, or a key landing on `#ta` closes it and sets the tab to `'text'` (`hide(true)`); a tab switch or the main screen also closes it but keeps the tab's view. The live terminal and PTY are untouched. While open, focus sits on the overlay body (so keys scroll it and Ctrl+C copies a selection instead of reaching Claude), the document click handler doesn't refocus `#ta` for clicks inside it, and the SCR and ●↑/●↓ buttons scroll and jump the history. A key that still lands on `#ta` (keyboard toggle) closes the overlay and goes through to Claude. Entries render as chat bubbles (user right, including slash and `!` commands; Claude left; tool rows, command output and notes unbubbled between). Images are lazy-loaded thumbnails (in the user's bubble, which Claude's `[Image #n]` text precedes, or inside the tool call, or a plain `.h-media` row when the call isn't rendered, never an `.h-user` bubble, which `jump()` would count as a prompt) that open full size in the file viewer (`window.showImage`, the `show_file` overlay with a direct URL and no server reference to drop).
- **Attachments and other input** (`history.js`): uploads (`uploadFiles` in `app.js`, from a paste or drop anywhere) are routed by the tab they started on, not the tab active when they finish: a tab in the HTML view (`HistoryView.attach`, per `wantsHtml`) keeps the paths in `tab.hist.attach`, shown as removable chips above the message box, instead of typing them into Claude's prompt, where they'd be invisible and ride along with the next message. Sending pastes each path as its own bracketed paste (as a terminal drop does, so Claude turns an image path into `[Image #n]`), then the text, 40 ms apart, then Enter; a message can be attachments alone. `draftToTerminal` pastes them into the prompt the same way, without the Enter; with attachments the text is a timed paste too (not `#ta`'s diff, which would race the pastes). A paste anywhere in the overlay (`onPaste`) attaches files, and pastes text outside a text field into the message box. Button bar while open: ENT sends a non-empty message (empty: Enter goes to Claude, e.g. for a menu), Tab takes the suggestion into an empty box (otherwise it goes to Claude), and a custom button's text is inserted into the box (`HistoryView.key`/`insert`) unless it is a single character (e.g. `1` for a menu option) or contains control characters: those are keystrokes and go to Claude.
- **Pinned entry**: the 📌 button (left of reload) keeps somewhere to type in view while scrolled up, per mode; it is on by default and the state is remembered in `localStorage` (`webterm.historyPinned`, off only when `'0'`). In terminal mode, while scrolling up has cut off Claude's prompt box, a strip at the bottom of the visible viewport (`updateStrip`) shows a plain-text copy of it read from the xterm buffer: from the second-to-last `─` rule on the live screen (the top of the box) to the last drawn row, or from the cursor row when there aren't two rules, with the cursor cell marked, plus Claude's spinner line on top when one is in the 25 rows above (same `SPINNER` pattern as the history overlay's working status). It updates on the terminal's scroll/write/resize events; tapping it scrolls to the bottom. The history overlay always ends with a multiline message box (one element shared by all tabs; its unsent text is kept per tab in `tab.hist.draft`, saved when the overlay leaves a tab and restored when it opens one) (the last child of `.history-body`, after the conversation, as Claude's prompt box ends the terminal); `.history-body` is a flex column and the box has `margin-top: auto` (or the menu panel above it does), so it sits at the bottom of the view even when the conversation is shorter than the view; pinning only makes it `position: sticky` at the bottom of the view instead of scrolling with the content once it overflows. ↑ in an empty box, or with the cursor at its very start, recalls earlier user messages and commands from the log (newest first, each once at its latest use, `tab.hist.sent`, kept across `/clear`); further ↑ on the recalled text's first line steps back, ↓ on its last line steps forward and finally restores what was being typed; editing a recalled message ends the recall, and a tab switch mid-recall keeps what was being typed as the draft (`recallKey`). Enter (or the button) sends; on desktop Shift+Enter is a new line (touch keyboards have no Shift, so there a new line needs a paste). The message box spans the full width, and while it is on screen `clampButtons` ends the button column above it (scrolling the column if it doesn't fit), so the buttons never cover the send button when the mobile keyboard shrinks the view. Leaving the overlay for the terminal (×, Esc, TEXT, typing to `#ta`) carries an unsent message into Claude's prompt without submitting it (`draftToTerminal`): a single line is appended to `#ta` and goes through its input diff, so it stays editable; multi-line text is a bracketed paste, after which `#ta` is cleared. A tab switch keeps the draft in the box instead. The reverse happens on the HTML button (`toggle` → `terminalToDraft`): text typed in the terminal and not yet sent (`sentText`, what `#ta` mirrored) is erased from Claude's prompt with one DEL per code point and appended to the box's draft. A paste's `[Pasted text]` placeholder isn't in `sentText`, so it stays in Claude's prompt. Sending: first one DEL per code point of `sentText` (erasing whatever `#ta` had already mirrored into Claude's prompt), then the text as a bracketed paste, then `\r` 80 ms later so the Enter isn't read as part of the paste, then an early poll. The overlay is sized to `visualViewport` so the box stays above the mobile keyboard.
- **Menus** (`parseMenu`/`updateMenu` in `history.js`): Claude's interactive screens (approval prompts, the `--resume` session picker, `/model`) aren't in the log, so while one is on the terminal's live screen it is mirrored as a panel of buttons above the message box, re-parsed on every `onWriteParsed`. A menu is a row starting with a pointer (`❯`/`›`/`>`) plus sibling rows at the pointer's text column. If blank lines separate the rows (the `--resume` picker: session title, then `2 hours ago · master · 1MB` at the same indent), each blank-separated block is one option and blocks shorter than the highlighted one (the project-name heading) are dropped; otherwise (always, when the pointer row is numbered) deeper-indented rows continue the option above, and if ≥2 rows are numbered only those count, plus a bare `Submit` row (AskUserQuestion multi-select, drawn at the description indent). A plain rule normally ends the scan, but one with a numbered row right under it is crossed (AskUserQuestion draws one above "Chat about this"); a pointer row right under a rule is Claude's prompt line unless it is numbered. Options labelled "Type something" / "Tell Claude what to change" open a text field: sending moves to the option, types the text (Claude replaces the label with it in place) and presses Enter. ◀/▶ switch AskUserQuestion tabs (or adjust `/model` effort). The lines above it, up to a plain rule and skipping boxes (the picker's search field) and `╌` borders, become the panel's question; the last block of text below it becomes a key hint. The layouts were verified against real ConPTY captures of Claude Code 2.1 (trust prompt, `--resume`, `/model`, file-write and Bash approvals, plan approval, AskUserQuestion single/multi-select/free text/review), including the 40 ms key bursts a click sends. Scanning up from the bottom stops at a plain `─` rule, and a pointer row right under a rule is Claude's own prompt line, so the prompt box and the scrollback above it never read as a menu. Clicking an option sends one arrow key per step from the highlighted row, then Enter, each as its own frame 40 ms apart so Claude reads them as separate keypresses; ▲/▼/◀/▶/Enter/Esc buttons send single keys. While a menu is mirrored, the keyboard's arrows and Enter (unmodified) go to Claude too when focus is on the history body or a menu button, or in the message box while it is empty with nothing attached (`menuKey`); on a menu button reached with Tab, Enter clicks that button instead. Screens that aren't a pointer list still need the terminal. `webtermMenu()` in devtools dumps the live screen and what `parseMenu` made of it (and copies it). agy (1.5) draws the same prompt box and `>` lists, verified against ConPTY captures of its trust prompt, `run_command` approval (numbered, under a rule, "Requesting permission for:" above) and `/model` picker. Its differences are handled generically: a `↑/↓ …` key-hint row at the option column ends the list; a pointer row under a rule is only the prompt line if the rule starts at or left of the pointer (the picker's search field has an indented underline); when a blank line separates the list from a `◂`/`▸` slider row (the picker's models, then its effort slider) and the block reading leaves fewer than 2 options, it falls back to one option per row; rows with `◂`/`▸` aren't options; the title scan stops only at a column-0 rule; and a two-column or far-right status footer isn't part of the hint. Re-checked against Claude Code 2.1.331 captures of the trust prompt, `/model` and the slash-command list only (unchanged results); Claude approvals, AskUserQuestion and a populated `--resume` picker were not recaptured. For agy tabs the Model/Effort buttons send `/model` (agy's picker, effort via ←/→) instead of popouts.
- **Working status** (`parseStatus`/`updateStatus` in `history.js`): Claude's spinner line (`✻ Frosting… (5m 21s · ↓ 33.9k tokens · esc to interrupt)`) isn't in the log either, so it is read from the live screen on the same `onWriteParsed` hook as menus and shown as an amber row at the top of the message box. It is looked for in the 25 rows above the prompt box's top rule (the todo list can sit between), only in its in-progress form (with `…`); the "esc to interrupt"/`ctrl+` hints are dropped, since Esc closes the overlay. `✻ Waiting for N background agent(s) to finish` (no `…`) also counts, but only with nothing but blank rows between it and the box, since it stays in the scrollback once the agent is done. agy's braille spinner (`⣽  Generating...`) matches the same pattern. agy's mode placeholder in an empty prompt (`Auto mode: … (shift+tab to cycle)`) is never taken as a suggested prompt.
- **Background tasks** (`parseTasks`/`updateTasks` in `history.js`): a blue `⧗ N … running` row under the working status while background shells/agents run, read from the live screen on the same hook. The count comes from Claude's footer below the prompt box's bottom rule (a `·`-separated segment like `1 shell` or `3 background tasks`); running agents from the rows under it (`( ) general-purpose  Pinging localhost  46s · ↓ 36.5k tokens`, squeezed to `Pin… 26s` on a phone). Claude draws nothing there when none run, so the row hides. Verified against ConPTY captures of Claude Code 2.1.330 at 110 and 50 columns.
- **Suggested prompt** (`parseSuggestion`/`updateSuggestion` in `history.js`): with its prompt empty, Claude may draw a suggested next prompt there as ghost text that Tab accepts. It is read from the live screen on the same hook: the row under the prompt box's top rule, after `❯`/`>`, through any wrapped rows to the bottom rule, and only if every visible character is dim, inverse or non-default colour (one normal-colour character means the user's own text is in the prompt). Claude's `Try "…"` placeholder examples are skipped. It becomes the message box's placeholder, and Tab in an empty box copies it in for editing (Shift+Tab and Tab with text still move focus). Touch keyboards have no Tab; the button bar's Tab sends it to Claude's own prompt instead.
- **Esc and focus**: the capture-phase Esc handler leaves Esc alone while a higher overlay is up (`.img-overlay`: file viewer, copy box; `.modal-overlay.visible`: dialogs), so Esc closes that instead of the history. `resetInput` (reload button → `hardRefresh`) refocuses the history body (`HistoryView.focus`) instead of `#ta` while the overlay is open, because a key on `#ta` would close it and reach Claude. Each poll is aborted after 15 s without headers or 2 min for the body, so a request hung by sleep or a network switch can't leave `busy` set. Polls are de-duplicated per tab (`tab.hist.busy`), so a slow request for one tab doesn't delay the first poll of the next.

### Clipboard push (`copy_text` MCP tool)

Lets a Claude session put text on the clipboard of the device viewing WebTerm (host → browser, like `show_file`).

- `McpCopyText` validates the text (≤ 1 MB), errors if no SSE client is connected, and broadcasts a `copy_text` SSE event (`{text, label}`) to all browsers. Nothing is stored server-side.
- The browser (`receiveCopyText` in `app.js`) first attempts a silent `navigator.clipboard.writeText`. Browsers gate this: Chrome/Edge require the document to be focused, Safari/iOS require a user gesture. On success a toast confirms the copy.
- If the silent write fails, a `copy-overlay` shows the text in a read-only textarea with a **Copy** button; the click supplies the user activation so `writeText` succeeds everywhere. If even that is blocked, it falls back to `execCommand('copy')`, and finally tells the user to select the text manually.

## Auth

Global middleware enforces HTTP Basic auth. Credentials are set on first run (console prompt), encrypted with DPAPI, stored in `webterm-settings.json`. All requests including `/ws` and static files require the `Authorization: Basic ...` header. Exception: `/mcp` is exempt from Basic auth — it uses its own DPAPI-encrypted API key validated via `?token=` query param.

### MCP Server

WebTerm exposes an MCP (Model Context Protocol) server at `POST /mcp?token=<key>`. JSON-RPC 2.0, Streamable HTTP transport. Tools:
- `open_tab(kind, projectId?, label?, command?)` — creates session, launches PTY, broadcasts SSE event. `kind` is one of `Agents.Kinds` (`powershell`, `claude`, `claude-resume`, `agy`, `agy-resume`). If `projectId` is omitted, defaults to the calling session's own project (resolved via `X-Webterm-Sid` header). `command` is handed to the process at spawn time, never typed into the PTY (typing it after a delay raced startup and arrived mangled):
  - `kind=claude` / `agy`: the initial prompt (agy's after `-i`). The agent (`AgentDef.Find`: `claude.exe` on PATH, or for an npm install `node.exe` + the package's `cli.js` behind the `claude.cmd` shim; `agy.exe` on PATH) is spawned **directly**, not via `cmd.exe /K`, because cmd re-parses `% ^ & "`, can't carry newlines and caps the line at 8191 chars. The tab therefore closes when the agent exits. Porta.Pty's built-in quoting mishandles backslash-before-quote, so the line is built with `VerbatimCommandLine = true` and `Agents.QuoteWindowsArg` (MSVC rules). A prompt starting with `-` gets a leading space so it isn't parsed as an option.
  - `kind=powershell`: passed as `-NoExit -EncodedCommand <base64 UTF-16LE>` (no escaping needed). The browser's "Add MCP" tab uses the same path via `defaultCommand`.
  - `*-resume`: rejected. Also rejected if the encoded command would exceed the Windows command-line limit (~32K).
- `close_tab(sid)` — disposes session, broadcasts SSE event
- `list_tabs()` — returns all active sessions with metadata
- `restart()` — rebuilds and restarts the WebTerm server, killing all sessions
- `show_file(path, caption?)` — displays a host file (by absolute path) in the browser's file viewer overlay; see below
- `copy_text(text, label?)` — puts `text` on the clipboard of every connected browser's device; see below

**Caller context (`X-Webterm-Sid`)**: the `claude mcp add` command generated by `POST /api/mcp-setup` includes `--header 'X-Webterm-Sid: ${WEBTERM_SID:-}'`. Claude expands `${WEBTERM_SID:-}` per-session at runtime, so each MCP call arrives with the caller's tab sid. The server uses it to inherit the caller's project when `open_tab` omits `projectId`. The `agy mcp add` command passes `${WEBTERM_SID}` the same way; whether agy expands it is unverified (if not, an agy caller must pass `projectId`). `agy --continue` resumes the cwd's last conversation (agy keys `cache\last_conversations.json` by workspace).

Setup: click "MCP" button on main screen → calls `POST /api/mcp-setup` (generates DPAPI-encrypted key, installs the agents' hooks) → opens PowerShell tab with the registration command (one part per agent CLI found on PATH). Key stored as `mcpKeyProtected` in settings.

### Tab attention notifications

Agent hooks notify WebTerm when an agent needs approval or finishes work. Setup is automatic via `POST /api/mcp-setup`.

**Server-side flow:**
1. `InstallAgentHooks` writes `~/.claude/hooks/webterm-notify.ps1` (args: `<event> [agent]`) and registers any missing `PermissionRequest`, `Stop` and `SessionStart` hooks in `~/.claude/settings.json`, and (if `~/.gemini/config` exists) a `webterm-notify` entry with `SessionStart`/`Stop` in agy's global `~/.gemini/config/hooks.json` (replaced when it differs; other entries kept), rewriting each file only when it changes. It runs from `POST /api/mcp-setup` and at every startup once setup has been done (`mcpKeyProtected` set), so a new script or hook reaches the agents without re-running setup. For Claude the script prints nothing (`SessionStart` only reports the transcript path, so it adds nothing to Claude's context); with the `agy` arg it prints `{}`, since agy reads a JSON object from every hook. It reads `transcript_path` (Claude) or `transcriptPath` (agy) from stdin, and skips agy's `stop` when `fullyIdle` is false (background tasks still running). agy has no permission-request hook (see `HistoryView.watch` below); its `SessionStart` fires on the conversation's first message, not at launch.
2. Agent sessions launch with `WEBTERM_SID` and `WEBTERM_NOTIFY_TOKEN` env vars
3. Hook fires → calls `POST /api/notify?token=<key>` with `{sid, event}`
4. Server records the body's `transcript` path on the session (any event; `Transcript.Preferred` swaps agy's reported `transcript_full.jsonl` for its smaller `transcript.jsonl` sibling), then maps events to SSE: `permission_request` → `tab_attention`, `stop` → `tab_idle` (`session_start` broadcasts nothing). `IsNestedAgent` drops events from an agent started inside the tab: more than one agent process (`claude.exe`/`node.exe`/`agy.exe`) between the hook and the PTY.

**Client-side behavior:**
- `window.raiseAttention(sid, kind)` (`app.js`) flags the tab and notifies; called for the SSE events, and by `HistoryView.watch` for agy tabs: each agy tab's live screen is checked (300 ms timer after output, skipped during a replay) for an approval menu (`parseMenu` title "Requesting permission…" or a numbered "No" option), raising `permission` when one appears
- Tab bar shows attention indicator (CSS classes `attention-permission`, `attention-idle`)
- Title flashes ("⚠ Approval needed" or "✓ <Agent> finished") when tab not visible
- Browser push notification via Notifications API (requests permission on load)
- Attention clears when user switches to the tab
